# آرتا کلین — پلتفرم تجهیزات نظافت صنعتی

سایت B2B تجهیزات نظافت صنعتی: کاتالوگ محصول + راهکار صنعتی + مشاوره فنی + خدمات
پس از فروش، به‌همراه پنل مدیریت. ساختار عمداً شبیه فروشگاه عمومی نیست؛ مسیرهای
خرید صنعتی (Problem → Solution → Product و RFQ به‌جای Checkout) در خودِ معماری
اطلاعات تعریف شده‌اند.

```bash
npm install
cp .env.example .env.local      # ADMIN_EMAIL و ADMIN_PASSWORD را پر کنید
npm run dev                     # http://localhost:3000
npm run build && npm start
npm run typecheck
```

**Node 24 الزامی است.** `node:sqlite` از Node 22.5 در دسترس شد ولی تا Node 23
پشت پرچم experimental بود و هر اجرا هشدار چاپ می‌کرد؛ در Node 24 پایدار شده.
روی Node 22 پروژه اجرا می‌شود اما لاگ سرور پر از `ExperimentalWarning` می‌ماند
و رفتار API تضمین‌شده نیست.

```bash
# اوبونتو — ارتقا به Node 24
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash - && sudo apt install -y nodejs
```

## مدل داده و مرز کد/دیتابیس

مشخصات فنی به‌صورت **صفت‌های نام‌دار** (`Spec[]` با `key`, `value`, `unit`)
نگهداری می‌شوند، نه ستون ثابت. افزودن دستگاهی با ۷۰ ویژگی متفاوت تغییر schema
نمی‌خواهد.

هر محصول سه لایه جدا دارد:

- **`specGroups`** — داده خام قابل مقایسه (ورودی موتور مقایسه)
- **`facets`** — مقادیر گسسته برای فیلتر
- **`fit`** — دامنه تناسب با نیاز (ورودی مشاور)

**کل محتوای سایت در دیتابیس است و از پنل قابل ویرایش.** یک جدول `content` برای
همه مجموعه‌ها، با بدنه JSON:

```
content(collection, slug, data, position, published, updated_at)
```

یک جدول به‌جای ده جدول، به همان دلیلی که `Spec[]` به‌جای ستون ثابت: شکل هر
مجموعه با گذشت زمان عوض می‌شود و هیچ فیلد تازه‌ای نباید یک `ALTER TABLE` و یک
دیپلوی بخواهد. در عوض:

- شکل هر رکورد با **توصیف فیلدها** در `src/lib/admin/schemas.ts` کنترل می‌شود؛
  فرم پنل از همان توصیف ساخته می‌شود.
- هر رکورد هنگام **خواندن** از `normalize*` در `src/lib/content.ts` رد می‌شود؛
  مقدار گمشده با پیش‌فرض پر و مقدار بدنوع دور انداخته می‌شود. نتیجه این است که
  یک رکورد خراب حداکثر خودش ناقص دیده می‌شود، نه اینکه صفحه ۵۰۰ بدهد.

`src/lib/data/*` از این پس **داده کارخانه‌ای** است: یک بار هنگام ساخت دیتابیس
به `content` کپی می‌شود (`src/lib/content/seed.ts`) و از آن لحظه مرجع، دیتابیس
است.

چیزی که عمداً در کد مانده، **واژگان موتورها** است: سطح، آلودگی، بازه متراژ،
تناوب، نوع دستگاه، منبع انرژی و نوع برس. این‌ها مقدار محتوا نیستند؛ ورودی
امتیازدهی مشاور، منطق فیلتر و تصویر برداری دستگاه‌اند و افزودن یکی‌شان کد
می‌خواهد، نه ویرایش.

### جدول‌ها

`users` · `sessions` · `content` · `settings` · `quotes` · `media`

نسخه schema با `PRAGMA user_version` کنترل می‌شود. `migrate()` اول همین عدد را
می‌خواند و اگر به‌روز باشد هیچ نوشتنی نمی‌کند — وگرنه workerهای موازی build روی
یک فایل SQLite به هم قفل می‌خورند.

### تنظیمات

`settings` فقط چیزهایی را نگه می‌دارد که از پنل عوض شده‌اند؛ پیش‌فرض‌ها در
`src/lib/site.ts` می‌مانند و هنگام خواندن ادغام می‌شوند. پس افزودن یک کلید تازه
به تنظیمات، هیچ مهاجرتی لازم ندارد و روی نصب‌های موجود هم بلافاصله مقدار درست
می‌گیرد.

سه سند: `site` (هویت و تماس)، `home` (متن‌های صفحه اصلی و محصولات منتخب)،
`nav` (منوی اصلی، گروه‌های مگامنو، ستون‌های دستی فوتر).

## موتورها

**`src/lib/advisor.ts`** — امتیازدهی وزن‌دار روی سطح (۳۰)، آلودگی (۳۰)، متراژ
(۲۸، بر اساس هم‌پوشانی بازه‌ای) و تناوب (۱۲). خروجی علاوه بر درصد تطابق،
`reasons` و `caveats` برمی‌گرداند تا کاربر بتواند پیشنهاد را قضاوت کند. مصرفی‌ها
از رتبه‌بندی اصلی خارج و جدا پیشنهاد می‌شوند.

**`src/lib/filters.ts`** — فیلتر وجهی با شمارش زنده؛ وضعیت در query string.

**`src/lib/search.ts`** — جست‌وجوی نیت‌محور: «روغن روی کف کارخانه ۵۰۰۰ متر» به
`/advisor?surface=factory-floor&dirt=oil&area=2000-10000` تبدیل می‌شود.

**`src/components/compare/CompareScreen.tsx`** — ردیف‌ها از اجتماع مشخصات ساخته
می‌شوند، ردیف‌های دارای تفاوت برجسته و بهترین مقدار هر ردیف علامت‌دار.

هر چهار موتور داده را **به‌صورت پارامتر** می‌گیرند و خودشان کاتالوگ را
نمی‌خوانند. دلیلش این است که از کامپوننت کلاینت هم صدا زده می‌شوند و کاتالوگ در
دیتابیس است: کادر جست‌وجوی هدر و جدول مقایسه با Server Action کار می‌کنند، و
صفحه دسته‌بندی و مشاور، فهرست خودشان را از صفحه سرور می‌گیرند. نتیجه این است که
کل کاتالوگ دیگر در باندل کلاینت نیست.

## پنل مدیریت

- **ورود**: scrypt (`node:crypto`) + نشست کوکی httpOnly در SQLite.
- **نخستین حساب**: فقط وقتی جدول کاربران خالی است و `ADMIN_EMAIL` و
  `ADMIN_PASSWORD` ست شده‌اند ساخته می‌شود. بدون این شرط یک رمز پیش‌فرض در کد
  می‌ماند که روی هر نصبی یکسان است. حساب‌های بعدی از `/admin/users`.
- **محتوا**: ده مجموعه — محصولات، دسته‌بندی‌ها، برندها، صنایع، خدمات، مقالات،
  پروژه‌ها، قطعات، نمایندگی‌ها و صفحات. برای هرکدام افزودن، ویرایش، کپی، حذف،
  پیش‌نویس/انتشار و ترتیب دستی.
- **تنظیمات**: متن‌های صفحه اصلی، منوها، هویت برند و راه‌های تماس.
- **تصاویر**: هر آپلود با sharp به WebP و حداکثر ۱۶۰۰ پیکسل تبدیل می‌شود؛ نام
  فایل از هش محتوا ساخته می‌شود، نه از نام کاربر.
- **درخواست‌ها**: فرم RFQ سایت مستقیم اینجا می‌آید، با وضعیت قابل تغییر.

### ویرایشگر عمومی

پنل برای هر مجموعه یک فرم دستی ندارد؛ `src/lib/admin/schemas.ts` هر مجموعه را
توصیف می‌کند و `RecordEditor` فرمش را می‌سازد. افزودن یک فیلد تازه به محصول =
یک سطر در آن فایل.

دو مسیر پویا کل CRUD را پوشش می‌دهند:

```
/admin/c/[collection]          فهرست، ترتیب، انتشار
/admin/c/[collection]/new      ساخت
/admin/c/[collection]/[slug]   ویرایش، کپی، حذف
/admin/settings/[key]          site · home · nav
```

ویرایشگر کل رکورد را در state نگه می‌دارد و هنگام ذخیره یک JSON می‌فرستد، نه
فیلد‌به‌فیلد FormData: برای «گروه مشخصات ← مشخصه‌ها» (آرایه‌ای از اشیاء که خودش
آرایه دارد) نام‌گذاری تودرتوی FormData هم نوشتنش شکننده است و هم خواندنش.

هر Server Action تغییردهنده خودش نشست را بررسی می‌کند — نه فقط صفحه‌ای که فرم
را نشان داده؛ Server Action یک endpoint عمومی است. اعتبارسنجی عمیق بدنه عمداً
آنجا انجام نمی‌شود، چون `normalize*` هنگام خواندن همان کار را برای هر رکورد —
از هر منبعی — انجام می‌دهد.

## سیستم بصری

پالت خنثی به‌علاوه یک Accent صنعتی. رنگ برند فقط Accent است، نه رنگ‌آمیزی کل
سایت. همه توکن‌ها در `@theme` در `src/app/globals.css` — تعویض رنگ برند یک‌جا.

دو سطح رنگی داریم، نه یکی: سطح روشن (کاتالوگ) و سطح عمیق (Hero، سربرگ صفحات،
فوتر، پنل). تناوب این دو، صفحه را از حالت «فهرست بی‌پایان کارت» بیرون می‌آورد.

اعداد مشخصات فنی با کلاس `.num` رندر می‌شوند: لاتین، `tabular-nums`,
`direction: ltr`. **این کلاس نباید روی عنصر `absolute` با `start`/`end` یا روی
عنصری با `ms-*`/`me-*` بیفتد** — چون `direction` را عوض می‌کند و جهت ویژگی‌های
منطقی برعکس می‌شود.

### Motion

- Lenis با ticker مشترک GSAP اجرا می‌شود؛ دو حلقه `rAF` جدا، انیمیشن اسکرول را
  یک فریم عقب می‌اندازد و لرزش دیده می‌شود.
- بخش «مسیر کار» با ScrollTrigger pin می‌شود و اسکرول عمودی را به حرکت افقی
  ترجمه می‌کند. فقط روی دسکتاپ؛ لمسی اسکرول معمولی می‌گیرد.
- صحنه سه‌بعدی Hero فقط با نمایشگر بزرگ + WebGL + نبود `prefers-reduced-motion`
  لود می‌شود؛ در غیر این صورت همان تصویر برداری. هیچ دارایی بیرونی لود نمی‌کند
  (`Environment preset` و `useGLTF` از CDN می‌گیرند و بی‌صدا شکست می‌خورند).
- همه‌جا `prefers-reduced-motion` رعایت می‌شود.

## نکته‌ای درباره build موازی

Next صفحات را هنگام build در چند worker **جدا** prerender می‌کند. هر worker یک
پروسه است و همه به یک فایل SQLite وصل می‌شوند. دو جا به همین دلیل شکل گرفته‌اند:

- `migrate()` اول `PRAGMA user_version` را می‌خواند و اگر به‌روز باشد هیچ
  نوشتنی نمی‌کند. ساخت schema و seed داخل یک تراکنش `BEGIN IMMEDIATE` است، پس
  فقط نخستین پروسه می‌نویسد و بقیه منتظر می‌مانند و بعد فقط می‌خوانند.
- `PRAGMA journal_mode = WAL` در `try` است. این تنها دستوری است که
  `busy_timeout` شاملش نمی‌شود و اگر اتصال دیگری باز باشد بی‌درنگ `SQLITE_BUSY`
  می‌دهد. شکستش بی‌اهمیت است: مقدار در خود فایل دیتابیس ذخیره می‌شود، پس یک بار
  که ست شد برای همیشه WAL می‌ماند.

با تغییر ساختار جدول‌ها، `SCHEMA_VERSION` را در `src/lib/db/client.ts` یک واحد
بالا ببرید.

## داده نمونه

`src/lib/data/*` داده کارخانه‌ای است: ۱۸ محصول، ۱۱ صنعت، ۳ برند، ۷ خدمت،
۲۰ قطعه، ۶ مقاله، ۶ پروژه، ۶ نمایندگی و ۱۶ صفحه. برندها و مدل‌ها ساختگی‌اند و
اعداد برای نمایش ساختار نوشته شده‌اند.

این‌ها فقط **یک بار**، هنگام ساخته شدن فایل دیتابیس، به جدول `content` کپی
می‌شوند. از آن پس ویرایش‌ها در دیتابیس‌اند و تغییر این فایل‌ها هیچ اثری روی
نصب موجود ندارد. برای شروع از صفر: سرویس را بخوابانید، فایل `DATABASE_PATH` را
پاک کنید و دوباره بالا بیاورید.
