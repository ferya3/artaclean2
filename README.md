# آرتا کلین — پلتفرم تجهیزات نظافت صنعتی

معماری و پیاده‌سازی یک سایت B2B تجهیزات نظافت صنعتی: کاتالوگ محصول + راهکار صنعتی +
مشاوره فنی + خدمات پس از فروش. ساختار عمداً شبیه فروشگاه عمومی نیست؛ مسیرهای خرید
صنعتی (Problem → Solution → Product و RFQ به‌جای Checkout) در خودِ معماری اطلاعات
تعریف شده‌اند.

```bash
npm install
npm run dev      # http://localhost:3000
npm run build
npm run typecheck
```

استک: Next.js 15 (App Router) · React 19 · TypeScript · Tailwind CSS 3 · بدون وابستگی
runtime دیگر. RTL کامل (`dir="rtl"`, `lang="fa"`).

---

## ۱. معماری اطلاعات

```
HOME
├── PRODUCTS            /products, /products/[category], /products/[category]/[slug]
├── SOLUTIONS           /solutions, /solutions/[industry]
├── FIND YOUR MACHINE   /advisor
├── BRANDS              /brands, /brands/[slug]
├── SERVICES            /services, /services/[slug]
├── KNOWLEDGE           /knowledge, /knowledge/[slug]
├── SPARE PARTS         /spare-parts
├── COMPARE             /compare
├── RFQ                 /quote
├── SEARCH              /search
└── COMPANY             /company/{about,projects,representatives,certifications,contact}
```

سه مسیر ورود موازی طراحی شده، چون سه نوع کاربر وجود دارد:

| کاربر | نقطه شروع | مسیر |
| --- | --- | --- |
| می‌داند چه می‌خواهد | دسته‌بندی محصول | `/products/[category]` با فیلتر وجهی |
| مسئله دارد، مدل نمی‌داند | مشاور یا صنعت | `/advisor` یا `/solutions/[industry]` |
| مالک دستگاه است | قطعه | `/spare-parts` با مدل یا شماره فنی |

## ۲. مدل داده

`src/lib/types.ts` مرجع کامل است. تصمیم اصلی: مشخصات فنی به‌صورت **صفت‌های نام‌دار**
(`Spec[]` با `key`, `value`, `unit`) نگهداری می‌شوند، نه ستون ثابت. بنابراین افزودن
دستگاهی با ۷۰ ویژگی متفاوت تغییر schema نمی‌خواهد و همین ساختار مستقیماً به EAV/JSONB
یا یک CMS headless نگاشت می‌شود.

هر محصول سه لایه جدا دارد:

- **`specGroups`** — داده خام قابل مقایسه (ورودی موتور مقایسه)
- **`facets`** — مقادیر گسسته برای فیلتر (`machineType`, `powerSource`, `areaMin/Max`, …)
- **`fit`** — دامنه تناسب با نیاز کاربر (`surfaces`, `dirt`, `frequency`) — ورودی مشاور

جدا نگه داشتن این سه، دلیل این است که هر سه موتور (فیلتر، مقایسه، مشاور) بدون
if-های موردی روی یک منبع داده کار می‌کنند.

## ۳. موتورها

**`src/lib/advisor.ts`** — امتیازدهی وزن‌دار روی سطح (۳۰)، آلودگی (۳۰)، متراژ (۲۸،
بر اساس هم‌پوشانی بازه‌ای نه تطابق دقیق) و تناوب (۱۲). خروجی علاوه بر درصد تطابق،
`reasons` و `caveats` برمی‌گرداند تا کاربر بتواند پیشنهاد را قضاوت کند نه صرفاً قبول.
مصرفی‌ها از رتبه‌بندی اصلی خارج و به‌عنوان «مکمل» جدا پیشنهاد می‌شوند — بازه متراژ
نامحدودشان وگرنه همیشه بالای دستگاه‌ها می‌نشیند.

**`src/lib/filters.ts`** — فیلتر وجهی با شمارش زنده هر گزینه؛ وضعیت در query string
است تا لینک قابل اشتراک باشد. فیلتر متراژ بر اساس هم‌پوشانی بازه کار می‌کند.

**`src/lib/search.ts`** — جست‌وجوی نیت‌محور. علاوه بر تطبیق واژگانی روی شش نوع
موجودیت، از جمله فارسی «سطح / آلودگی / متراژ» را استخراج می‌کند: «روغن روی کف کارخانه
۵۰۰۰ متر» مستقیماً به `/advisor?surface=factory-floor&dirt=oil&area=2000-10000` تبدیل
می‌شود. نقطه اتصال برای جایگزینی با جست‌وجوی معنایی، تابع `scoreText` است — بقیه
امضاها تغییر نمی‌کند.

**`src/app/compare/page.tsx`** — ردیف‌ها از اجتماع مشخصات ساخته می‌شوند (نه لیست
ثابت)، ردیف‌های دارای تفاوت برجسته می‌شوند، بهترین مقدار هر ردیف علامت می‌خورد، و
بالای جدول به پرسش «کدام مناسب شماست؟» پاسخ داده می‌شود.

## ۴. تصمیم‌های UX

- **CTA اصلی دستگاه‌های سنگین «درخواست پیش‌فاکتور» است، نه «افزودن به سبد».**
  `priceMode: "rfq" | "listed"` روی هر محصول این را کنترل می‌کند؛ مصرفی‌ها قیمت
  مستقیم دارند.
- **فرم RFQ مرحله‌ای است و اطلاعات تماس آخر می‌آید** — بعد از اینکه کاربر روی
  مشخصات پروژه وقت گذاشته.
- **نوار CTA چسبان موبایل** (مشاوره / درخواست قیمت / تماس) به‌جای دکمه بزرگ سبد.
- **Motion فقط جایی که کارکرد دارد**: شمارش اعداد KPI هنگام ورود به viewport،
  با احترام به `prefers-reduced-motion`.
- **مشخصات فنی**: ابتدا خلاصه اسکن‌شدنی، بعد «مشخصات کامل» با یک کلیک.

## ۵. سیستم بصری

پالت خنثی (`#F5F5F3` / `#FFFFFF` / `#111111` / `#666666` / `#E5E5E5`) به‌علاوه یک
Accent صنعتی. رنگ برند فقط Accent است، نه رنگ‌آمیزی کل سایت. همه مقادیر به‌صورت CSS
Variable در `src/app/globals.css` تعریف شده‌اند — تعویض رنگ برند یک‌جا انجام می‌شود.

فونت: **Vazirmatn** (آزاد) پیش‌فرض است. برای Peyda / Dana / IRANSansX فقط `--font-fa`
و `@font-face` عوض می‌شود. اعداد مشخصات فنی با کلاس `.num` رندر می‌شوند: لاتین،
`tabular-nums`، `direction: ltr` — این کلاس فقط برای مقادیر عددی/لاتین است و نباید
دور متن فارسی بیفتد.

## ۶. SEO

URLهای معنایی، `generateStaticParams` برای همه صفحات محصول/دسته/صنعت/برند/خدمت/مقاله،
`generateMetadata` با canonical، JSON-LD نوع `Product` روی صفحه محصول، و
`sitemap.ts` / `robots.ts` تولیدشده از همان داده کاتالوگ.

## ۷. داده نمونه

`src/lib/data/*` داده seed است: ۱۸ محصول، ۱۱ صنعت، ۳ برند، ۷ خدمت، ۲۰ قطعه، ۶ مقاله و
۶ پروژه. برندها و مدل‌ها ساختگی‌اند و اعداد برای نمایش ساختار نوشته شده‌اند — هنگام
اتصال به کاتالوگ واقعی باید با دیتاشیت سازنده جایگزین شوند. ساختار صفحات و موتورها
مستقل از این مقادیر کار می‌کنند.

## ۸. محاسبه حقوق و دستمزد (`/payroll`)

ابزار داخلی: روز کارکرد و ساعت اضافه‌کاری وارد می‌شود، فیش حقوقی ماه بیرون می‌آید —
مزد پایه، پایه سنوات، حق مسکن، بن کارگری، حق اولاد، اضافه‌کاری/شب‌کاری/جمعه‌کاری/
تعطیل‌کاری/نوبت‌کاری، کسر بیمه سهم کارگر و مالیات پلکانی، خالص پرداختی و هزینه کل
پرسنل (با سهم کارفرما).

```
src/lib/payroll/config.ts   ← تنها فایلی که هر سال به‌روزرسانی می‌شود
src/lib/payroll/calc.ts     ← فرمول‌ها (توابع خالص، بدون React)
src/lib/payroll/money.ts    ← تبدیل ریال/تومان و پارس اعداد فارسی
src/components/payroll/PayrollCalculator.tsx  ← فرم و فیش
```

**به‌روزرسانی سالانه:** بعد از انتشار بخشنامه مزد، یک بلوک به آرایه `payrollYears`
اضافه کنید (حداقل مزد روزانه، پایه سنوات، حق مسکن، بن، حق اولاد، نرخ بیمه و پله‌های
مالیاتی). محاسبه‌گر خودش جدیدترین سال را پیش‌فرض می‌گیرد و سال‌های قبل برای محاسبه
معوقات سر جای‌شان می‌مانند. هیچ کد دیگری تغییر نمی‌کند.

نکته‌ها:

- واحد ذخیره‌سازی **ریال** است، دقیقاً مثل بخشنامه، تا موقع کپی‌کردن ارقام تبدیلی لازم
  نباشد؛ نمایش پیش‌فرض تومان است و تبدیل فقط در `money.ts` انجام می‌شود.
- سالی که `draft: true` داشته باشد در رابط کاربری با هشدار «پیش‌نویس» نمایش داده
  می‌شود. ارقام هر سال باید پیش از استفاده رسمی با متن بخشنامه تطبیق داده شود.
- حق اولاد طبق قانون از بیمه و مالیات معاف است و در `insurableBase` نمی‌آید.
- صفحه `noindex` است و در `sitemap`/منو نیست؛ ابزار داخلی است نه صفحه بازاریابی.
- ورودی‌ها در `localStorage` می‌مانند تا ماه بعد فقط کارکرد عوض شود. دکمه «چاپ فیش»
  فقط فیش را چاپ می‌کند (استایل چاپ در انتهای `globals.css`).

## ۹. قدم بعدی برای production

1. جایگزینی `src/lib/data/*` با یک لایه داده (Laravel API، CMS headless یا Route
   Handler) — امضای توابع `getProduct` / `productsByCategory` / … همان می‌ماند.
2. اتصال `handleSubmit` در `QuoteForm` به CRM یا صف پیش‌فاکتور.
3. تصاویر واقعی محصول به‌جای `ProductImage` (placeholder فعلی) و افزودن دامنه‌ها به
   `next.config.mjs`.
4. جایگزینی `scoreText` با ایندکس معنایی برای جست‌وجو.
5. i18n در صورت نیاز به نسخه انگلیسی (ساختار مسیرها آماده است).
6. اتصال `/payroll` به لیست پرسنل و ذخیره فیش‌های ماهانه (فعلاً تک‌نفره و روی مرورگر).
